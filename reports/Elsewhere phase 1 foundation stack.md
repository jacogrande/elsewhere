# Elsewhere's phase 1 leans on Bun and Miniflux

Phase 1 of Elsewhere can be built on about fifteen runtime packages (eight on the server), because Bun 1.4 now covers the database, scheduler, password hashing, legacy charset decoding, HTTP decompression, test runner and single-binary packaging. The few libraries worth adding are Hono 4.13 for the API, Zod 4 for boundaries, **feedsmith** for RSS/Atom/JSON Feed/OPML parsing, **sanitize-html** with a Miniflux-style allowlist, htmlparser2, normalize-url and ipaddr.js in the pure core, and React 19.3 with TanStack Router, Query and Virtual plus Tailwind 4 in the SPA. The research supports most of architecture.md but asks for fourteen changes. The biggest are: drop Drizzle for plain SQL migrations (Drizzle 1.0 is still an RC taking breaking changes), schedule with `Bun.cron`, use code-based TanStack routing (there is no Bun plugin), model starred as its own flag, add entry tombstones and a split feed-state table, index search with an FTS5 external-content table, and never pair DOMPurify with linkedom or happy-dom. The feed-fetching rules are where a new reader most often goes wrong, and Miniflux, FreshRSS and Yarr have already paid for those lessons in code: conditional GETs, a one-hour floor, honoring Retry-After, a per-host limit of one, no request bursts on add or startup, and defensive handling of duplicate GUIDs. Infrastructure stays small: one compiled binary on a distroless image, published multi-arch to GHCR, one SQLite volume, and `VACUUM INTO` backups. Several findings rest on single-machine local tests or secondary sources, so run five short spikes before you write feature code: TypeScript 7 compatibility, a 50–100 feed parser corpus, the compiled build, the sanitizer and the SSRF-safe fetcher.

## About fifteen packages, because Bun covers the rest

Most of what a reader needs is now built into Bun 1.4.4 (released 2026-10-22). Bun 1.4 added in-process **`Bun.cron`**, `bun test --parallel/--isolate/--changed`, fake timers, and static directory routes, and it cut HTTP server memory use by 13–48% under load ([Bun 1.4 blog](https://bun.com/blog/bun-v1.4)). `bun:sqlite` provides WAL, cached statements and synchronous transactions ([Bun SQLite docs](https://bun.com/docs/runtime/sqlite)). Bun's `fetch` decompresses gzip, deflate, br and zstd by default and documents an address-pinning pattern for SSRF defense ([Bun fetch docs](https://bun.com/docs/runtime/networking/fetch)). Bun 1.3.6 bundled SQLite 3.51.2, so `RETURNING` (which needs 3.35 or later) and FTS5 are available ([Bun blog index](https://bun.com/blog); [DEV Community](https://dev.to/arthurpro/you-probably-dont-need-redis-put-the-job-queue-in-your-sqlite-file-624)). Every added library has to justify itself against that baseline.

### feedsmith wins the parser slot, provisionally

feedsmith is the best answer so far to architecture.md's open question about the XML parser. It depends only on fast-xml-parser and entities, has about 182k weekly downloads, and was last published 2026-09-25 ([npm](https://www.npmjs.com/package/feedsmith)). In the researchers' local tests on Bun 1.4.2, it was the only parser that recovered **both items** from a malformed RSS file (unescaped `&`, bare `<br>`, `&nbsp;`), and it was the only one to auto-detect JSON Feed from the same `parseFeed` call. The runner-up, @rowanmanning/feed-parser 2.1.5, resolves relative links for you, but it has no JSON Feed support and garbled a malformed item ([README](https://github.com/rowanmanning/feed-parser)). feedsmith leaves normalization to the caller. Relative Atom links come back raw, and `type="html"` titles keep their entities encoded, so a test-first `toFeedEntry()` mapper in `core/feeds` must resolve URLs, decode titles, pick content in the order content:encoded → Atom content → description, and choose dates. That fits the architecture well. The weak point is the evidence: the benchmark is self-published by feedsmith's author, and the tolerance results come from a handful of synthetic inputs. That is why the corpus spike below comes first.

### Sanitize in core with Miniflux's allowlist

sanitize-html fits the "pure core, no DOM" rule. It takes about 0.09 ms per call versus about 1 ms for DOMPurify with jsdom (local test). Its default allowlist drops every `<img>`, though, so it must be configured explicitly. Copy Miniflux's rules: an explicit tag→attribute map; `script`, `style` and `noscript` dropped with their content, along with `hidden` elements; 1×1 and 0×0 pixel-tracker images removed; feedburner, stats.wordpress and share-intent URLs blocked; `src`, `href`, `poster`, `cite` and every `srcset` candidate rewritten to absolute URLs with tracking parameters stripped; iframes allowed only from YouTube, Vimeo, Bandcamp and similar domains, with a `sandbox` attribute; and `rel="noopener noreferrer"`, `referrerpolicy="no-referrer"` and `loading="lazy"` added ([sanitizer.go](https://github.com/miniflux/v2/blob/main/internal/reader/sanitizer/sanitizer.go)). Each rule is a `transformTags` or `exclusiveFilter` hook, so each gets its own unit test. There is one maintenance caveat. sanitize-html's standalone GitHub repo is **archived**, and releases now come from the apostrophecms monorepo ([archived repo](https://github.com/apostrophecms/sanitize-html)). It is still published regularly (2.18.2 on 2026-11-11, about 18M weekly downloads), but watch it. If it ever stalls, the fallback is DOMPurify 3.4.18 with jsdom, isolated in an adapter. Never use DOMPurify with linkedom or happy-dom. Sanitize when storing, so the database only holds safe HTML, and back that up with a strict CSP from Hono's `secureHeaders`.

## One binary, one volume, one backup command

**Dev.** Run the API, the SPA (with HMR through `development: { hmr: true, console: true }`) and the worker in one process ([Bun fullstack docs](https://bun.com/docs/bundler/fullstack)). Prefer `bun --watch` for the server over `bun --hot`. `--hot` reloads modules in place, so it can start a second worker loop and a second cron unless both are guarded by a `globalThis` singleton; browser HMR still covers the SPA. Keep the dev database at a gitignored `./.data/dev.db`. Add a `bun run seed` script that imports a bundled OPML of 10–20 stable feeds, and a `db:reset` script. Bun loads `.env` automatically, so no dotenv is needed. Validate env with a plain Zod schema and `z.prettifyError`. @t3-oss/env-core's client/server split isn't needed for server-only config. Never inline secrets into the SPA bundle. Bun only replaces literal `process.env.PUBLIC_*`, so serve runtime config from `/api/config` instead ([Bun fullstack docs](https://bun.com/docs/bundler/fullstack)).

**Tests.** `bun test` covers every layer. Run SQLite adapters against `:memory:`: migrate once, call `serialize()`, then `Database.deserialize()` for each test ([Bun SQLite docs](https://bun.com/docs/runtime/sqlite)). Test the fetcher against a local `Bun.serve({ port: 0 })` that replays recorded fixtures: ETag/304, 301 vs 302, 410, 429 with and without Retry-After, slow bodies, and a Cloudflare challenge. Test HTTP with `app.request()`. Turn on happy-dom only in DOM test files, so core tests don't pay for a DOM and the sanitizer can never pick up a happy-dom global. Call RTL `cleanup()` in `afterEach`, because files share one window unless you use `--isolate` ([Bun DOM testing docs](https://bun.com/docs/test/dom)).

**CI.** Use one GitHub Actions workflow on `oven-sh/setup-bun` v2.2.0 ([releases](https://github.com/oven-sh/setup-bun/releases)) that runs `bun install --frozen-lockfile`, `tsc --noEmit`, `biome ci`, `depcruise` (enforcing §4's import rules), `bun test`, and finally a smoke test that compiles the binary, starts it against an empty database, applies migrations from inside the binary, and hits `/readyz`. On a tag, cross-compile from one Linux runner. Bun targets `bun-linux-x64/arm64`, their `-musl` variants, darwin and windows, and `--bytecode` works when cross-compiling since 1.4.1 ([Bun executables docs](https://bun.com/docs/compiler/executables); [Bun blog index](https://bun.com/blog)). Then build an amd64 + arm64 image with buildx. Copy the pre-built binary per `TARGETARCH` instead of compiling under QEMU. Publish to GHCR with SHA-256 checksums. Skip macOS binaries in phase 1, or document Gatekeeper's quarantine flag.

**Distribution.** Importing the HTML file in server code embeds the SPA in the `--compile` binary, and `Bun.serve` serves it from a manifest ([Bun executables docs](https://bun.com/docs/compiler/executables)). Two details matter. First, Bun's docs say plugins "work with the `Bun.build()` JS API but not yet with the CLI," so write the build as a `scripts/build.ts` that passes the Tailwind plugin to `Bun.build`, not as a bare `bun build` command ([Bun fullstack docs](https://bun.com/docs/bundler/fullstack)). Second, migrations must be inside the binary: import each `.sql` file `with { type: "text" }` or embed the folder with `--asset`. Use a multi-stage Dockerfile that builds on `oven/bun:1.4` and runs on `gcr.io/distroless/cc-debian12` as non-root, with `VOLUME /data` and `DATABASE_PATH=/data/elsewhere.db`. Distroless has no curl, so ship a `healthcheck` subcommand for Docker's `HEALTHCHECK`, as Miniflux does ([Miniflux Docker docs](https://miniflux.app/docs/docker.html)). Avoid alpine/musl until you measure a size benefit. Phase 1 loads no SQLite extensions, so the binary really is self-contained. That changes in phase 3, when sqlite-vec's native `.so` must ship beside it.

**Hosting.** Self-hosters expect what Miniflux ships: multi-arch images with pinned and `latest` tags, a compose file, and a healthcheck ([Miniflux Docker docs](https://miniflux.app/docs/docker.html)). Elsewhere's version is simpler, with one service and one named volume (no Postgres container), plus a two-line Caddyfile for HTTPS. Trust `X-Forwarded-*` headers only when configured to, and keep in mind that Hono's `csrf()` relies on `Origin`/`Sec-Fetch-Site`, which some proxies strip ([Hono CSRF docs](https://hono.dev/docs/middleware/builtin/csrf)). For a public demo, use one Fly.io machine with one volume and a nightly reset. Fly's own advice of "at least two volumes per app" is for high availability, which a demo doesn't need ([Fly volumes](https://docs.fly.io/volumes/overview)).

**Backups.** WAL "does not work over a network filesystem," and a database separated from its `-wal` file can lose transactions or become corrupted ([SQLite WAL docs](https://www.sqlite.org/wal.html)). The README must therefore say two things: never put `/data` on NFS or SMB (a common Unraid/TrueNAS mistake), and never `cp` a live database. Ship an `elsewhere backup <path>` subcommand and an optional daily job that runs `VACUUM INTO` and rotates N copies. Document `sqlite3_rsync` for live copies over SSH ([sqlite3_rsync docs](https://www.sqlite.org/rsync.html)). Offer Litestream v0.5.18, which is actively maintained, as an optional sidecar in docs only ([Litestream releases](https://github.com/benbjohnson/litestream/releases)). Skip LiteFS, which hasn't had a release since April 2025 ([GitHub](https://github.com/superfly/litefs/releases)). For observability, phase 1 needs `/healthz`, a `/readyz` that checks the database and migrations, JSON-lines logs, a startup line with version, SQLite version and `journal_mode`, and the failed-jobs and feed-health admin view.

## A schema that already knows Miniflux's 136 migrations

Miniflux started with a small schema and grew to about **136 additive migrations**. The late additions show what Elsewhere should model from day one: `starred` as a separate boolean, `changed_at`, per-feed `user_agent`, `cookie`, `ignore_http_cache`, `disabled`, `next_check_at`, and finally an `entry_tombstones` table that replaced a `removed` status so deleted entries stop coming back ([migrations.go](https://github.com/miniflux/v2/blob/main/internal/database/migrations.go); [storage/entry.go](https://github.com/miniflux/v2/blob/main/internal/storage/entry.go)). Yarr's single `UNREAD=0, READ=1, STARRED=2` enum makes "starred" and "read" mutually exclusive, which is the mistake Miniflux had to undo ([model.go](https://github.com/nkanaev/yarr/blob/master/src/storage/model/model.go)). Yarr also splits volatile fetch state into a `feed_states` table, and FreshRSS keeps a free-form `attributes TEXT` column on feeds that absorbs per-feed settings without migrations ([yarr migration.go](https://github.com/nkanaev/yarr/blob/master/src/storage/postgres/migration.go); [FreshRSS schema](https://github.com/FreshRSS/FreshRSS/blob/edge/app/SQL/install.sql.sqlite.php)). The proposed phase-1 tables keep architecture.md's context prefixes:

| Table | Key columns | Lesson it encodes |
|---|---|---|
| `feeds_folder` | id, title UNIQUE, position | One level of folders; doubles as GReader labels later |
| `feeds_feed` | id, url UNIQUE, site_url, title, folder_id NULL, `settings` JSON, identity_strategy, disabled, created_at | User-edited metadata only; JSON settings avoid Miniflux's long run of ALTERs |
| `feeds_feed_state` | feed_id PK, etag, last_modified, body_hash, last_fetched_at, next_check_at, health `ok\|degraded\|failing\|gone`, error_count, last_error, redirect_target, redirect_count, hub_url | Yarr's split keeps hot writes off the feed row; body hash skips unchanged bodies |
| `feeds_entry` | id INTEGER PK, feed_id, **hash** (identity), guid (raw), url, normalized_url, content_hash, first_seen_at, last_seen_at, provenance, UNIQUE(feed_id, hash) | Identity, content hash and arrival times are kept separate (FreshRSS has both `guid` and `hash`) |
| `feeds_entry_tombstone` | (feed_id, hash) PK, deleted_at | Checked before every insert, as Miniflux does |
| `library_article` | id INTEGER PK, entry_id UNIQUE, feed_id, canonical_url, title, author, html (sanitized), text (plain), word_count, published_at, `is_read`, read_at, `starred`, starred_at, changed_at, enclosures JSON | Starred is separate from read; `changed_at` enables incremental sync later |
| `library_article_fts` | FTS5 external content over `title, text` | Text is stored once, not twice |
| `jobs` | id, kind, payload JSON, status, attempts, run_at, locked_until, lock_token, last_error, dedupe_key (partial UNIQUE while queued/running) | Lease plus token for crash recovery |
| `auth_session`, `settings` | hashed session id, expiry; key → JSON value | Single-user auth; secrets never sent to the SPA |

A few of these choices need explanation. The FTS table copies Yarr's FTS5 migration: `content='items'`, `content_rowid='id'`, `unicode61`, insert/delete triggers, and an update trigger narrowed to `AFTER UPDATE OF title, content` so that marking an article read doesn't rewrite the index ([yarr sqlite migration.go](https://github.com/nkanaev/yarr/blob/master/src/storage/sqlite/migration.go)). Indexing a plain-text column that the core produces avoids Yarr's `strip_html` SQL function. Index bloat is a real risk: one Miniflux user found a **9.7 GB** full-text index over about **74 MB** of entries ([discussion #2056](https://github.com/orgs/miniflux/discussions/2056)). So run FTS `optimize` and `PRAGMA optimize` in a maintenance job. Integer article ids and `changed_at` leave room for a Google Reader API later. FreshRSS lists about 19 GReader clients against 2 Fever clients ([FreshRSS README](https://github.com/FreshRSS/FreshRSS/blob/edge/README.md)), but neither API belongs in phase 1. `first_seen_at`, `last_seen_at` and `provenance` keep future RFC 5005 backfill from flooding "new" items ([RFC 5005](https://www.rfc-editor.org/rfc/rfc5005)).

Open the database once and share that one connection between HTTP and the worker. Open it with `strict: true`, then run `PRAGMA journal_mode=WAL; synchronous=NORMAL; foreign_keys=ON; busy_timeout=5000`. Run every write in a synchronous `.immediate()` transaction. Bun's transaction function "must be synchronous — work after an `await` runs outside the transaction" ([Bun SQLite docs](https://bun.com/docs/runtime/sqlite)), and that fits load → decide → apply exactly: do network I/O first, then apply the plan in one synchronous block. Claim jobs with a single `UPDATE … WHERE id IN (SELECT … LIMIT n) RETURNING *`, requeue rows whose lease has expired at startup and on every tick, and complete them with `WHERE id=? AND lock_token=?` ([gqs](https://pkg.go.dev/github.com/romanqed/gqs/sql); [blog.master.dev](https://blog.master.dev/?p=10923)). One pragmatic refinement to §8: enqueue one `entries.ingested` job per refresh carrying all the new entry ids, rather than one job per entry. Contexts still talk only through jobs, and the queue doesn't fill with a row for every blog post.

## Polling rules that keep Elsewhere off blocklists

Feed publishers do punish bad readers. Rachel Kroll's feed policy, as quoted on Hacker News and in reader issue trackers, allows conditional requests **at most once an hour**, answers faster polling with 429, and she blocked one reader outright for polling every two minutes ([HN](https://news.ycombinator.com/item?id=40498024); [NewsBlur forum](https://forum.newsblur.com/t/rachel-by-the-bay-feed-challenge-and-excessive-timeouts-probably-not-respecting-retry-after/10710)). NetNewsWire got 429s simply because adding a feed fired two or three GETs in a row ([NetNewsWire #4531](https://github.com/Ranchero-Software/NetNewsWire/issues/4531)). The scheduling decision is a pure function, so these rules are cheap to write test-first.

**Next poll time.** Port Miniflux's `ScheduleNextCheck`: interval = `7 days / weekly entry count`, clamped to [min, max] (the max when last week had no entries), then raised to `max(interval, RSS ttl, Cache-Control max-age, Expires, Retry-After)`, then capped at the max ([model/feed.go](https://github.com/miniflux/v2/blob/main/internal/model/feed.go)). Use a **1-hour floor and 24-hour cap** with jitter, not Miniflux's 5-minute entry-frequency minimum. Take two constants from FreshRSS: clamp server cache hints to between 60 s and 1 day, and when a 429/503 has no Retry-After, wait **1,500 s**, capped at **172,800 s** ([config.default.php](https://github.com/FreshRSS/FreshRSS/blob/edge/config.default.php)). Parse Retry-After as either seconds or an HTTP date, as Miniflux does ([response_handler.go](https://github.com/miniflux/v2/blob/main/internal/reader/fetcher/response_handler.go)).

**Requests.** Store validators and send them back exactly. Sending both `If-None-Match` and `If-Modified-Since` is correct, because RFC 9110 requires servers to ignore the latter when the former is present ([RFC 9110 §13.1.3](https://www.rfc-editor.org/rfc/rfc9110#section-13.1.3)). Send `Accept-Encoding: br, gzip` and an honest `Elsewhere/<version> (+url)` User-Agent. Set a **20 s** timeout and a **15 MB** body cap, Miniflux's defaults ([options.go](https://github.com/miniflux/v2/blob/main/internal/config/options.go)), and count *decompressed* bytes, because Bun decompresses transparently. Allow one request per host at a time and four to eight `feed.poll` jobs overall. Store a hash of the body as well, so a 200 with an unchanged body skips all database work ([SparkleMuffin](https://virtualtam.github.io/sparklemuffin/developer-guide/concepts/feed-polling-caching.html)). Adding a feed takes **one GET**, and its response serves both discovery and the first parse. Don't refetch right after subscribing, and spread first polls with jitter instead of refreshing everything at startup. A single `Bun.cron("* * * * *")` tick enqueues due feeds with `dedupe_key = poll:<feedId>`. Bun waits for the handler to finish before computing the next fire time, so "invocations never stack" ([Bun cron docs](https://bun.com/docs/runtime/cron)).

**Classifying outcomes.** `planRefresh` maps each fetch outcome to a health change. A **304** just touches the validators. A **301 or 308** updates the stored URL, but only after several consecutive identical permanent redirects, since RFC 9110 lets clients rewrite references on permanent redirects only ([RFC 9110 §15.4](https://www.rfc-editor.org/rfc/rfc9110#section-15.4)); a **302, 303 or 307** keeps the original URL. A **410** marks the feed `gone` and stops polling ([§15.5.11](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.11)), while **404 and 5xx** mark it `failing` with backoff. A **403 carrying `cf-mitigated: challenge` and an HTML body** becomes a distinct `blocked_by_challenge` error, which Miniflux detects but doesn't try to solve. After **three consecutive parse errors**, automatic polling stops; unlike Miniflux, which drops such feeds silently ([storage/feed.go](https://github.com/miniflux/v2/blob/main/internal/storage/feed.go)), Elsewhere should show this to the user with a "retry" button.

**Fetching safely.** Disable automatic redirects (`redirect: "manual"`, at most 5 hops) and re-run the SSRF check on every hop. That check resolves DNS, rejects private, loopback, link-local, multicast and unspecified addresses after unwrapping NAT64 and IPv4-mapped forms (Miniflux's `IsNonPublicIP` rules), and pins the connection to the checked IP ([url.go](https://github.com/miniflux/v2/blob/main/internal/urllib/url.go); [Bun fetch docs](https://bun.com/docs/runtime/networking/fetch)). An `ALLOW_PRIVATE_NETWORKS` setting, off by default, serves LAN feeds. Decoding happens in the shell, in this order: BOM, then the XML declaration, then the HTTP charset. In local tests, Bun's `TextDecoder` handled windows-1252, koi8-r, shift_jis, gbk, big5 and the other legacy encodings, so iconv-lite isn't needed. In the same tests, the fast-xml-parser-based parsers rejected XXE and didn't expand billion-laughs entities. Defer WebSub: the hub must reach a public callback URL, which a NATed home server usually lacks ([W3C WebSub](https://www.w3.org/TR/websub/)). Store `hub` and `self` links when parsing so WebSub can be added later.

**Entry identity.** Port Miniflux's hash chain: SHA-256 of the GUID. If that GUID repeats within one document, hash GUID|URL, then GUID|index, because "some feeds ship the same GUID for every entry". With no GUID, hash the URL, and as a last resort the title plus content ([rss/adapter.go](https://github.com/miniflux/v2/blob/main/internal/reader/rss/adapter.go)). Add FreshRSS's auto-degrade: when invalid GUIDs exceed 5% of a fetch, the feed's identity strategy switches to link-based unless the user forced it ([Feed.php](https://github.com/FreshRSS/FreshRSS/blob/edge/app/Models/Feed.php)). Coerce JSON Feed numeric ids to strings ([JSON Feed 1.1](https://www.jsonfeed.org/version/1.1/)). Keep the fragment for identity but strip it when canonicalizing articles. If more than N entries look new at once, treat it as a likely CMS migration and don't mark them all unread. When content changes, update it quietly through `content_hash` without marking the entry unread, which is FreshRSS's default ([config-user.default.php](https://github.com/FreshRSS/FreshRSS/blob/edge/config-user.default.php)).

**Retention.** Elsewhere's vision wants permanent archives, which runs against every mature reader's defaults. Miniflux deletes read entries after 60 days and unread ones after 180; FreshRSS keeps 3 months, between 50 and 200 per feed; Yarr keeps 90 days relative to each feed's newest arrival ([options.go](https://github.com/miniflux/v2/blob/main/internal/config/options.go); [config-user.default.php](https://github.com/FreshRSS/FreshRSS/blob/edge/config-user.default.php); [item.go](https://github.com/nkanaev/yarr/blob/master/src/storage/sqlite/item.go)). So delete nothing by default. If a purge option is added, it writes tombstones, never touches starred entries, and anchors on per-feed `last_seen_at` the way Yarr does, so an item still present in the feed can't be purged and then re-imported.

### The MVP is the feature set Miniflux, FreshRSS and Yarr share

Miniflux, FreshRSS and Yarr share a baseline feature set ([miniflux reader](https://github.com/miniflux/v2/tree/main/internal/reader); [yarr routes](https://github.com/nkanaev/yarr/blob/master/src/server/routes.go)). Phase 1 should ship that baseline plus architecture.md's skeleton items. That means password login with a session cookie (and a bearer token for scripts); subscribe by URL with `<link rel="alternate">` discovery and Miniflux's fallback probe list, with redirects off on each probe ([finder.go](https://github.com/miniflux/v2/blob/main/internal/reader/subscription/finder.go)); OPML import and export plus a JSON export of everything; one level of folders; separate read and starred flags; mark-all-read by feed, folder or all, bounded by the newest article id at click time so new arrivals stay unread; FTS5 search; feed health with manual refresh; feed icons and enclosures; a virtualized timeline with j/k/m/s/o shortcuts; and a responsive layout. About six routes cover this: timeline, feed, article, search, settings and login. Defer these to later phases or behind flags: Google Reader and Fever APIs, full-text scraping (the adapter can exist, opt-in per feed and only for new entries, as Miniflux does ([processor.go](https://github.com/miniflux/v2/blob/main/internal/reader/processor/processor.go))), rewrite rules, filters, an image proxy, WebSub, backfill and multi-user.

## Run five spikes before feature code

Several recommendations rest on evidence weaker than it looks. The **local tests** (feedsmith's malformed-feed recovery, the DOMPurify + linkedom passthrough, legacy `TextDecoder` support, XXE and billion-laughs resistance) ran on one machine with Bun 1.4.2 and small synthetic inputs; none was a corpus evaluation, and the linkedom result was not checked in Node. feedsmith's speed lead comes from its **author's own benchmark**. **Rachel Kroll's rules** are secondhand: her site refused connections from the research environment, so the one-hour limit and the startup-burst rule come from HN quotes, forum threads and issue trackers, though RFC 9110 independently supports sending validators back exactly.

Other claims rest only on **secondary sources**: shadcn defaulting to Base UI, Hono v5 removing `hono/<adapter>` imports (an aggregator), automatic React Fast Refresh in Bun (a docs mirror), no code splitting in `--compile` builds (a third-party summary), FreshRSS's 20-minute refresh floor, and the Docker image-size estimates. Still **unverified** are `Bun.password`'s argon2id default (from prior knowledge), the `z.prettifyError` name, whether bun-plugin-tailwind 0.1.2 (not updated in about 13 months) works with Tailwind 4.3, whether `--bytecode` works with HTML-import builds, how dependency-cruiser treats `bun:*` imports, jest-dom 7 typings under `bun:test`, whether Bun's `fetch` honors a custom `tls.serverName` when connecting to an IP literal, and how Miniflux persists a 301 on refresh. The CSP string in the frontend notes is a proposal, not a sourced recommendation.

The five spikes below address the riskiest of these. Together they take about a week, and each produces code you keep.

| # | Spike | Pass condition | Fallback |
|---|---|---|---|
| 1 | **TypeScript 7 compatibility**: a minimal repo with Hono RPC across two sub-apps, `@types/bun`, Biome, dependency-cruiser with `bun:*` imports, and jest-dom matchers | `tsc --noEmit` is clean, `hc` types match TS 6, and the depcruise rules fire on a planted violation | Pin TypeScript 6.x/5.9 |

## Conclusion

The research changes what phase 1's risk is. The risk isn't the framework stack: Bun, Hono and React are stable and well documented, and most library slots resolve to "Bun already does it." It sits in the feeds context's edge cases: duplicate GUIDs, permanent versus temporary redirects, servers that rate-limit impolite readers, hostile HTML, and SSRF through user-supplied URLs. Miniflux, FreshRSS and Yarr each shipped those fixes years after launch, one migration at a time. Elsewhere can start with all of them in place, and almost every one is a pure function: `planRefresh`, `nextCheckAt`, `entryHash`, `identityStrategy`, `sanitize`, `isPublicAddress`, `findFeedLinks`. The test-first rule in architecture.md therefore lands exactly where the bugs historically were. Recorded fixtures from the corpus spike become a test suite most hand-built readers never had.

The second implication concerns later phases. Plain SQL migrations, an FTS table that stores text once, separate read and starred flags, `changed_at`, and provenance plus first-seen timestamps cost almost nothing now. They also leave room for embeddings, a sync API and archive backfill without rebuilding any tables. Phase 1 already avoids the dependencies most likely to break, namely ORM release candidates, DOM shims and worker-thread loggers, so the main dependency risk left by phase 3 is sqlite-vec's native library.
